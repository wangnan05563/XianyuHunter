# 整体结论（健康度评估 · Top 3 · 短期路线）

> 数据来源：`REPORT.md`（实测口径）、`OPTIMIZATIONS.md`（20 条建议）、`results/*`（原始样本聚合）。
> 本文不引入任何新数字，只做判断与排序。

## 1. 健康度评估

**一句话结论：作为「单人本地工具」健康；作为「多人共用的控制台服务」亚健康 —— 瓶颈不在正确性，而在容量形态。**

| 维度 | 评级 | 判据（实测） |
|---|---|---|
| 单用户响应体验 | **良好（局部差）** | 基线三组 P50 均为 10~11 ms，绝大多数接口 P95 < 200 ms；但有 **7 类接口在零并发下就已是几百毫秒到 1.1 s**（`anticrawl/strategy` 1 094.7 ms→已降 905 ms（C4 ①③，2026-11-03）、`vector-admin/snapshots` 451/233.8 ms、`auth/me` 152.6 ms **← 该条已于 2026-11-03 从「固有成本」重新归类：隔离沙箱实测 `/me` c=1 只有 8~10 ms，152.6 是被长尾抬起来的平均（原始样本 p50 85.6 / p95 490.1），属排队而非固有成本，详见 OPTIMIZATIONS §C2 落地记录**、`config/raw` 132.4 ms、`prices/category-comparison`、`maintenance/status` 单发 1.6 s→已降至完整重算 188/170 ms（A4，2026-11-03；归因是 `.venv-build` pycache 漏排除，不是表计数）），属固有成本，与并发无关 |
| 并发容量 | **偏弱** | 首屏/统计聚合读拐点 **4 并发**（TPS 封顶 81.2 后回落）、混合控制台读 **16 并发**、幂等写 **8 并发**。96 并发时轻组 P95 3 893.2 ms、P99 4 296.9 ms，已进入「界面不可用」区间 |
| 吞吐 | **偏低且与并发解耦** | 读侧上限约 **80 rps**（单进程 GIL + 同步 handler 挤同一线程池）；写侧上限约 **66 tps**，16 并发反而 −22% |
| 正确性 | **良好** | 全程 0 个 5xx（除环境性的 `links/live`）、**0 次 `database is locked`**、无高并发专属的竞态错误（未见 UNIQUE 冲突 / 锁边界缺陷）。写路径在容量范围内是正确的 |
| 长期稳定性 | **内存通过；4 h 延迟/吞吐不通过（含口径保留）** | **内存**：4 h 长跑（12 并发 / 135 接口 / 14 401.4 s）8 段 P95 包络 366.4 → 430.8 MB（+17.5 MB/h），但 96 次 >60 MB 的大幅归还（最大 162.4 MB）证明**能归还、非单调累积**；全局斜率 +20.4 → 后 1/4 +11.6 MB/h 有衰减，按吞吐归一化 0.19 MB/(TPS·h)（30 min 轮 1.20）；末段 P95 增量 +13.4 且 `max` 首破 500 MB，故**只能判「4 h 内无可用性风险」**，不能写「已收敛」。**延迟/吞吐**：同一夹具下 4 h 轮 TPS 105.8（30 min 183.1，**−42%**）、p50/p95/p99 79.91/283.51/703.17（30 min 50.93/144.35/314.35），即 **4 h 尺度上出现了明显退化**；已排除「5xx/崩溃」（5xx=0、`000` 24 条）与「SQL 索引」（最慢的 `tasks/options` SQL 仅 2.24 ms、加索引无收益）；**先前的两条推断已被 A/B 实验双双证伪**（`rerun_ab_pool_probe.py` / `results/rerun_ab_pool_probe.json`：把库灌到 12 000 行后 `tasks/options` 单发 **10.9 ms**、8 并发 p95 255.5 ms；「重接口 8 并发 + 廉价 1 并发」下廉价接口 p95 **60.2 ms**、反而低于对照的 96.2 ms）→ **成因未定位**；**「Python 客户端 GIL」也已排除**（JMeter 独立 JVM、同样 12k 行 / 12 并发下 `tasks/options` p50 仅 **164 ms**、p95 403）→ 三条解释（数据量 / 池传染 / Python 客户端）逐一否掉，只剩 **4 h 运行期累积的服务端状态或当时的系统状态**。详见 REPORT §8.8 第 3/4 点 |
| 资源水位 | **有裕量但结构受限** | CPU 均值 56.1%、峰值 269%（多核折算）—— 单进程模型下多核未被用满，属**软件形态限制而非机器饱和**；RSS 峰值 414.5 / 私有内存峰值 617.7 MB；WAL checkpoint 持续回收，库文件未见无界增长 |
| 可观测性 | **中** | 依赖不可用时用 503 表态（30 min 内 795 次全部来自同一接口，占本轮 5xx 的 100%），真实故障信号会被这类噪声淹没。**✅ E3 已落地（2026-11-03）**：`links/live` 的 `scheduler_off` / `browser_unavailable` 改为 HTTP 200 + 流内 error 事件，UI 行为不变；复跑后这 795 次不应再计入 5xx |
| 数据增长抗性 | **偏弱（最大远期风险）** | 当前 items 774 / events·evaluations 数万，已经是百毫秒级；被过滤的 5 个列**无索引**，`/api/evaluations` 每请求全量拉 `eval.*`（limit=50000）+ Python 侧过滤分页。这类实现随采集累积**线性恶化**，且恶化不可通过加并发缓解 |

> 关于「亚健康」的限定：本结论的绝对吞吐受客户端能力压低（`python_replay` 96 并发已近上限、负载机与服务同机），因此 P95/P99 是**上界**、拐点绝对位置可能右移；但「拐点相对次序」「饱和形态（吞吐封顶 + 排队增长）」和「零并发固有慢接口」三项与机器无关，构成可信判断。详见 `REPORT.md` §6。

## 2. Top 3 优先处理问题

### ① 缓存击穿 + 同步线程池共享：高并发尾延迟爆炸与超时（影响面最大）

- **症状**：单用户 avg 50 ms 的接口，12 并发长跑变 200.5 ms；轻组 48→96 并发 P95 从 2 064.0 劣化到 3 893.2 ms，真实缺陷率单调升至 **3.17%**；`maintenance/status` 曾出现 P95 **60 033 ms**（客户端 60 s 超时），而它单发只要 1.6 s（该 1.6 s 底噪已由 A4 降到完整重算 **188/170 ms**，见 ②）。
- **根因链**：测时版本的 `web/cache.py`（`_make_sync_wrapper` / `_make_async_wrapper`）冷/过期 miss **无 single-flight** → N 个并发各自重算同一聚合（同族 `stats` 接口齐处 165~200 ms 窄带，正是「大家都在等同一份重算」的指纹）；重算占住 anyio 默认 40 token 线程池 → 连 8.4 ms 的 `notifier/quiet-hours` 在 96 并发被拖到 **2 096.8 ms**（完成样本从 55 掉到 7）；`services/cache_scan.py:52,66` 的进程级 `RLock` 再把 `/cache-scan` 与 `/maintenance/status` 串行化。
- **对应措施**：B1（单飞，约 20 行）✅ **已于 2026-10-31 落地，本文数字全部是修复前基线** + B5（SWR 的「后台刷新」其实在请求线程里跑，见 REPORT 表 B9）✅ **同日落地** + ~~B2（慢接口纳入 TTL）~~ **复核后 5 项撤回 4 项**（`cache-scan` 是推进状态机、`snapshots`/`strategy` 的旧值会被用户当场看见、`config/raw`+`share` 前端不消费且会把明文凭据放进进程缓存；反证见 OPTIMIZATIONS §B2）+ D1（慢同步接口独立线程池）✅ **2026-11-04 落地**（16 条实测最重的同步接口改走 `CapacityLimiter(4)` 专用道；生产同形沙箱里廉价接口 p50 **3 509.6 / 1 153.9 → 34.3 / 59.8 ms**、60 s 完成样本 **16/34 → 504/334**，`queue_p95` **974 → 6.7 ms** 而 `work_p50` 恒 ~4 ms —— 排队这一环被拆开证实。三处口径修正：原文建议的 `anyio.to_thread.RunVars` 装机 anyio 4.13 不存在；`logs/search` 压测样本全是 422、没有实测占用故不入道；接口级 P95/缺陷率仍要同一 JMX 复跑。详见 OPTIMIZATIONS §D1 落地记录）+ D2（解锁）✅ **2026-11-05 落地**（`cache_scan` 的时间片改到锁外走，同一路径同一时刻只留一个推进者、其余调用方立刻拿到当前进度：合成树（60 目录 × 300 文件 = 18 000 个文件 / 17.58 MB，一次全扫 50.3 ms，切片预算 2.51 ms）同路径 8 次并发到达 p95 **42.4 / 36.7 → 9.9 / 2.8 ms**、总墙钟 **44.4 / 38.0 → 11.9 / 4.6 ms**，跨路径 2×8 并发 **81.6 / 83.6 → 16.4 / 17.1 ms**，而扫到 `done` 的墙钟与逐字段读数不变（1 波 42.6 → 3 波 44.4 ms，终值 18 060 条目逐字段相同）。原文建议的「按路径分锁」判定不落 —— 生产只有一个 `_cache_scan` 实例、三个调用点都指向同一个 `_browser_data_dir()`，分锁解决的是并不存在的形态；「共享工作队列」候选实测更差（到 `done` 4~6 波、墙钟 **83.8 / 66.7 ms**，比现状长一倍），因为预算是墙钟：GIL 下 K 个并发切片只是把一片切碎。接口级 avg 与 96 并发数字仍待同一 JMX 复跑。详见 OPTIMIZATIONS §D2 落地记录）。B1 是**全场最大杠杆**。

### ② 请求路径上的重复文件/Socket 探测：与并发无关的固有成本（最易修、确定性最高）

- **症状**：7 类接口在**零并发**下就是几百毫秒到 1.1 s。
- **根因**：`modules/login_strategy.py:144` 每次请求对 CDP 端口做 `socket.create_connection(timeout=1.0)`（端口未开即吃满 1 s），随后 `:150-184` 打开 Chromium Cookie SQLite 做全表 `LIKE '%goofish%'`；`api_config.py` 的 `_load_yaml()` 每次重读并 `safe_load` 整个配置（绕过了 `infra/yaml_config.py` 的单例缓存）—— **落地复核时把这条根因又下钻了一层**：7.2 KB 的配置纯 Python `safe_load` 就要 52.5 ms，而本机 libyaml 在而未用（OPTIMIZATIONS C6，判据 `config_memo_probe.py`）；`api_vector_admin.py` 的 `_list_snapshots` 对同一目录调 `_dir_size` **两次**；`auth_query.py` 里 `_resolve_current_user_id` 被调用两次 + 每次都重读 cookies 文件、写库、查库。鉴权本身（带 300 s 缓存的 `verify_session`）**不是**瓶颈 —— 这个区分很重要，否则会优化错方向。
- **对应措施**：~~C6（换 libyaml 后端，成本最低、砍的是常量本身）~~ ✅ 2026-11-01 已落地读侧（解析 47.7 → 6.5 ms；写侧因 C dumper 把 emoji 写成转义、产物不再逐字节相同而撤回）+ ~~C1~~ ✅ 2026-11-03 已落地（双调用合并，实测 -43%；顺带把 `/status` 的同步走盘挪进 `to_thread`）+ ~~C4~~ ✅ 2026-11-03 已落地 ①③（关闭态探测 1 014→109 ms/请求；②短 TTL 因需配对失效不落，接口级约 190~250 ms）+ ~~A4~~ ✅ 2026-11-03 已落地（完整重算 2 235/5 205 → 188/170 ms；实测把原归因「6 张表计数」推翻 —— 每张仅 ~0.1 ms，真正成本是漏排除的 `.venv-build/` pycache）+ C3 + C2。这几条**改动小、收益可预测**（按实测地板参照 7~9 ms 估算），属"第 1 周就该走完"的那一档。C3 的 config 侧已随 B2 残留落地（memo 掉重复解析）；`api_templates` 那半也已于 2026-11-06 落地（文件指纹 memo + `_save_user` 写盘配对作废，进程内处理器 2.23 → 0.53 ms；模板文件只有 2 KB/30 KB，收益与 config 的 52 ms 解析不是一个量级，详见 OPTIMIZATIONS §C3）。

### ③ 无索引 + 全量重载/全内存导出：随数据增长线性恶化（远期最贵）

- **症状**：`/api/evaluations` avg 195.9 ms / P99 858 ms，`prices/category-comparison` 长跑 avg 580.2 ms，导出类 P99 1 827.7 ms，私有内存峰值 617.7 MB。
- **根因**：`infra/repo_events.py:337` 每次 `limit=50000` 全量拉 `eval.*` 后在 Python 侧过滤分页，`:357-364` 另发一次 COUNT；**⚠️ 落地复核（2026-11-04）把这条根因的范围收窄了**：真实库里 `eval.%` 命中 1 867 行、其中 1 490 行是通知事件 `eval.passed`（读完即丢），前缀 `LIKE` 走 `ix_events_created_type` 全表扫而等值走 `ix_events_type_created` —— 改等值后取数段 218.7/256.2 → 35.9/65.3 ms；但**压测身份 `user_id="default"` 读到的行数是 0**，所以本节的 195.9 ms 里不含这笔成本（那段并发排队归 D1），A2 的收益只在「账号里有评估数据」的真实用户路径上（详见 OPTIMIZATIONS §A2）；`db_models.py` 核对后确认 `items.price`、`evaluations.risk_level`、`price_history.user_id`、`orders.type`、`task_links.updated_at` **无索引**；`repo_error_logs.py:63-65` 用 `%LIKE%` 前后通配（索引天然不可用）；`api_export.py` 虽已用 `StreamingResponse`，但先把整份 CSV 拼进 `io.StringIO` 再一次性 yield（**D4 已于 2026-11-06 落地**）；`evaluations_list.py:69-80` 缓存 miss 时按 task_id 逐个跑 `_compute_sold_range`（N+1）。
- **对应措施**：~~A2（查询下推）~~ ✅ 2026-11-04 已落地（前缀→等值 + 去掉被丢弃的 COUNT；SQL 分页与聚合下推判定不落）+ ~~A2′（品牌归一化）~~ ✅ **2026-11-06 已落地**（正则预编译 + 别名表压缩结果预计算；`_compact_text` 73 251 → 2 367 次、`_enrich_eval_record` 占列表 60.8% → 39.5%、端点中位 148.2 → 121.5 ms；原文的「请求内 memo」被实测推翻 —— 377 条记录只有 363 个唯一 title，memo 版慢 15%，见 OPTIMIZATIONS §A2′）+ ~~A1（补索引）~~ ✅ **2026-11-06 已落地（5 条里落 3 条）**（`items.price` 区间过滤 15.09 → 7.17 ms、`evaluations.risk_level` 变覆盖索引扫描 3.45 → 2.17 ms、`orders.type` 改复合 `(type, created_at)` 使 4.08 → 0.50 ms 且去掉临时排序；`price_history.user_id` 与 `task_links.updated_at` 实测无收益，判定不落 —— 见 OPTIMIZATIONS §A1）+ ~~A5（前缀匹配/FTS5）~~ ❌ **2026-11-06 判定不落**（`error_logs` 只有 2 112 行、`%LIKE%` 1.8~10.0 ms，前缀对照反而不快；`logs/search` 的 `q` 是 Python 子串匹配、根本没有 SQL LIKE，下推 SQL 后延迟 33.7 → 37.7 ms —— 那是口径改进不是性能收益，见 OPTIMIZATIONS §A5）+ ~~D4（真流式）~~ ✅ **2026-11-06 已落地**（`api_export`/`api_logs` 改按块产出、日志文件分块读、`db-admin` 表导出改游标 + 分块：50 000 行 items 峰值 38.27 → 2.52 MB、40 MB 日志峰值 190.48 → 9.29 MB、18 403 行 events 导出 2 433 → 285 ms；原文「db-admin 也是全内存拼接」被实测推翻 —— 它本来就是流式，慢在逐行 yield × 线程池往返，见 OPTIMIZATIONS §D4）+ ~~C5（评估列表市场统计批量化）~~ ✅ **2026-11-06 已落地**（`compute_market_stats_batch` 的 cache miss 集合改走 `task_id IN (...)` 批量取数，与行情页共用同一段 `_summarize_price_stats`；20 个任务实测 40 条 SQL / 17.1 ms → 2 条 / 4.7 ms，任务越多比值越低 —— 见 OPTIMIZATIONS §C5）。

### Top 3 之外的一条未定论风险（不是结论，是待验证项）
