# 闲鱼 IM WebSocket 协议评估（T05073 / O-01 第①项）

> 评估日期：2026-11-10 ｜ 来源：`docs/requirements/优化需求.md` §3.1 O-01、§5 风险表
> 性质：**桌面调研 + 本项目静态核对**，不含真实协议抓包与线上账号联调。文中「社区反馈」类结论均为二手资料，未经本机实测，已在每条标注。
> 结论用途：决定 O-01 是「直接全量接入」还是「先做协议评估小步验证再全量接入」。

## 1. 结论与建议

**建议按需求原文走「小步验证」路线，本轮不直接全量替换 Buyer 页面轮询。**

| 判断 | 依据 |
| --- | --- |
| 协议**技术可行** | 社区已有多个可用实现（XianYuApis、pyxianyu、xianyu-auto-reply 系），私信实时收发链路（sign + base64 + Protobuf）已被完整逆向并开源 |
| 协议**不可作为唯一通道** | 非官方接口，闲鱼随时可改签名算法/Protobuf schema/风控策略；社区方案本身把「持续跟进协议更新」列为长期成本 |
| 本项目**具备低成本试错条件** | `requirements.txt:70` 已有 `websockets==16.0`；Cookie 三层管理、领域事件总线 + SSE 推送均已就绪，可复用 |
| 本项目**缺的是协议资产而非工程能力** | 缺 sign 算法 JS、Protobuf 消息 schema、Token 刷新细节、完整登录态 Cookie 的自动化获取；这些要么依赖上游实现，要么必须在真实账号上抓包验证 |

因此本轮交付边界为：**协议评估（本文）+ 与协议实现解耦的接入骨架（传输层抽象、事件订阅、重连、失效降级、日志/事件留痕）+ 单元测试**；真实协议编解码与线上联调留到 L1/L2 阶段。**降级到页面轮询的路径必须常备且默认开启**，这是需求原文和 §5 风险表的硬约束。

## 2. 协议现状（桌面调研）

闲鱼官方**未开放** IM 消息接口。社区做法是通过 Web 端私有协议维持一条长连接：

1. **握手**：用登录 `goofish.com` 后的**完整 Cookie**（含 httpOnly 字段，`document.cookie` 取不到）发起 WebSocket 连接，自定义 headers 携带 Cookie / User-Agent / Origin；随后交换设备 ID、用户信息与认证 token 完成注册。
2. **编解码**：`sign` 签名 + `base64` + `Protobuf` 三道关卡；部分实现描述为 MessagePack 序列化再 Base64，命名不统一，说明**不同版本/不同消息类型结构并不一致**，不能写死一套 schema。
3. **签名算法**：核心是逆向得到的 JS，主流实现采用「Python 主进程 + Node.js 子进程执行签名 JS」混合架构（Python 3.9+/3.7+、Node.js 18+），`static/goofish_js_*.js` 可热更新以对抗算法过期。
4. **保活**：心跳 + 断线重连；社区实现采用指数退避（1s 起、上限 30s），连续失败超阈值转诊断流程。Token 自动刷新用于维持长驻不掉线。
5. **消息面**：文字/图片消息、会话列表、历史聊天记录、主动发信、商品详情、媒体上传；订单状态/付款通知一般作为系统消息类型由同一通道下发。

> 上述为二手资料汇总（见 §9），具体字段、端点、消息号**未在本机验证**，不可直接据此写生产代码。

## 3. 参考实现对比

| 实现 | 定位 | 与本项目相关度 | 主要代价 |
| --- | --- | --- | --- |
| `cv-cat/XianYuApis` | 协议逆向基线库，HTTP + WS 双通道、asyncio | 需求原文点名的协议参考 | 需引入 Node.js 子进程执行签名 JS；协议随平台改版需跟进 |
| `DoLovya/pyxianyu` | 同类能力库，可 pip 安装 / 作 submodule，明确标注风控与封号风险 | 工程化更规整，可作 L1 阶段的协议适配器候选 | 仍是第三方维护，非官方契约；引入外部依赖需评估许可与供应链 |
| `xianyu-auto-reply(-fix)` / `XianyuAutoAgent` | 下游成品：多账号、自动回复、自动发货 | 可参考「每账号独立连接」「连接状态监控」的工程经验 | 与本项目 Buyer 抢单语义不同，不能整包搬运 |

**关键工程共识（社区）**：多账号必须**一账号一连接**，共用连接容易触发频率限制与断连；连接状态要有实时监控；Cookie 需加密存储并做过期检测。

## 4. 稳定性与风险清单

| # | 风险 | 证据/性质 | 缓解设计（本项目必须落地） |
| --- | --- | --- | --- |
| R1 | 平台改签名/Protobuf 导致协议整体失效 | 社区把「持续跟进协议更新」列为核心维护成本；二手资料 | 传输层与业务层解耦，协议适配器可替换；失效自动降级轮询 |
| R2 | 风控/封号 | `pyxianyu` README 明确「自动化操作账号存在被风控、限制功能甚至封号风险」；二手资料 | 默认关闭 IM 开关；不在连接失败时无限重试骚扰服务端；读多写少 |
| R3 | 登录态过期 | 实践反馈「cookie 每 6 小时要刷新」「WebSocket 断连后要重新登录」；二手资料 | 复用既有 Cookie 三层管理与 Token 续期；连续鉴权失败直接降级，不盲目重连 |
| R4 | IM 接口频率限制 | 社区反馈「一天几百单的重度场景，IM 有频率限制」；二手资料 | 重连指数退避 + 最大次数 + 冷却；事件去抖，不把 WS 消息直接放大成抢单动作 |
| R5 | 长连接假死（TCP 在、消息不来） | WebSocket 通用问题 | 心跳 + 「最近一次有效消息时间」看门狗，超时判定失效并降级 |
| R6 | 第三方协议库供应链/许可 | 静态判断 | 不在本轮引入新第三方协议依赖；适配器接口留好，由后续裁决决定引入哪一个 |
| R7 | 打包体积与运行时 | `websockets==16.0` 已在锁文件内；Node.js 子进程签名则需新增运行时依赖 | 若走 JS 签名路线，需单列打包/部署评估（参考 `docs/requirements/打包体积优化评估报告-20261102.md`） |

## 5. 与本项目现状的契合度

| 已有能力 | 位置 | 可复用点 |
| --- | --- | --- |
| `websockets==16.0` | `requirements.txt:70` | 客户端长连接无需新增 Python 依赖 |
| 领域事件枚举与严重度 | `backend/xianyu_hunter/domain/events.py`（`EventType`、`EVENT_SEVERITY`、`severity_of`） | 新增 IM 连接/降级/消息事件，统一走既有通知与 SSE 通道 |
| SSE 推送 | `backend/xianyu_hunter/web/routes/sse_stream.py` | 前端无需新建实时通道 |
| Cookie 三层管理、Token 续期 | `modules/` 下 Cookie 相关模块（详见探查报告） | 握手凭据来源，避免另建一套账号状态 |
| Buyer 页面轮询 | `backend/xianyu_hunter/modules/buyer.py` | **必须保留**，作为降级底座 |

**缺口**：sign 算法 JS、Protobuf schema、注册/心跳报文格式、完整 httpOnly Cookie 的自动化提取、真实账号联调环境。这些决定了「L1 只读订阅」之前必须先做 L0 协议探针。

## 6. 分级实施路线（小步验证）

| 阶段 | 目标 | 通过判据 | 本轮是否交付 |
| --- | --- | --- | --- |
| **L0 协议评估** | 明确可行性、风险、降级契约 | 本文 + 任务回写 | ✅ 本轮 |
| **L1 骨架自证** | 与协议无关的传输层抽象、事件订阅、重连、降级、日志/事件留痕 | 单元测试：断线重连退避、连续失败降级、降级后仍走轮询、事件落库/推送、开关默认关闭不改变现有行为 | ✅ 本轮 |
| **L2 协议探针** | 用真实账号 + 完整 Cookie，验证握手/签名/解码能否收到一条真实消息 | 需要用户提供授权账号与 Cookie；产出报文字段表与 schema | ❌ 需人工授权 |
| **L3 只读订阅** | 订阅买家消息/订单状态/上架提醒，转成领域事件，与轮询并行双跑对比 | 秒级到达（<3s）、双跑一致性、无风控告警 | ❌ 依赖 L2 |
| **L4 全量接入** | Buyer 订阅订单状态变更替代轮询 | 断网重连自动恢复、协议失效自动降级且有日志/事件 | ❌ 依赖 L3 |

> 需求原文「建议先做协议评估小步验证再全量接入」，与上表一致：**协议编解码不能在无真实账号的情况下自称完成**。

## 7. 降级契约（硬约束）

1. **轮询路径常备**：IM 只是「快路径」，任何情况下不得删除或绕过 Buyer 现有轮询。
2. **默认关闭**：`im_websocket.enabled` 默认 `false`，未显式开启时行为与当前版本逐字节一致（不建连、不占端口、不改事件面）。
3. **失效判定要保守**：握手鉴权失败、连续重连超阈值、心跳看门狗超时、解码连续出错，任一触发即降级；降级原因必须同时写**结构化日志**与**领域事件**，可在事件时间线查到。
4. **降级不可逆自动升回**：降级后不允许自动重试升回 IM（避免抖动放大），需人工确认或经过冷却期后由显式操作恢复。
5. **不把消息直接变成业务动作**：WS 消息先转领域事件，抢单仍走既有决策链，避免协议抖动直接触发下单。

## 8. 验收口径与不可自证项

- 可自证（L1）：单元测试覆盖重连退避、降级触发、降级后轮询仍被调用、事件/日志留痕、开关默认关闭。
- **不可自证**：需求验收里的「买家消息秒级到达（<3s）」「断网重连后自动恢复」中的真实链路部分、「协议失效时自动降级」中的真实失效部分——这些必须有真实平台连接。本轮只能证伪「模拟失效」，不能证「真实协议在工作」。
- 因此 T05073 **不应在本轮标记 verified / done**；应保留待办，等 L2/L3 的真实联调证据。
