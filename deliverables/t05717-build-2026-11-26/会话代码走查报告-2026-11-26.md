## 2. 高优先级问题（建议下次发布前修复）

### H1. Full/Lite 判定链仍有断点：整个 Chromium 目录被删后会误走下载

**位置：**

- `backend/xianyu_hunter/infra/browser_kernel.py:190-216`（`is_bundled_build`）
- `backend/xianyu_hunter/infra/browser_kernel.py:310、327`（缺失后进入下载分支）
- `backend/xianyu_hunter/infra/browser_kernel.py:155、564-569`（`.xh-full-bundle` 写在 `playwright_browsers` 目录内部）
- `scripts/launcher.py:101-106`（按 `playwright_browsers` 是否存在决定 `PLAYWRIGHT_BROWSERS_PATH`）

**问题：**

`is_bundled_build()` 先要求 `root/playwright_browsers` 目录存在，再检查该目录里的 `.xh-full-bundle`。但标记文件本身就在这个目录里：

```python
pw = root / "playwright_browsers"
if not pw.is_dir():
    return False
if (pw / _BUNDLE_MARKER).is_file():
    return True
```

因此，如果 Full 安装后整个 `playwright_browsers` 目录被杀软隔离、用户清理或安装异常删除：

1. 标记文件随目录一起消失；
2. `is_bundled_build()` 返回 `False`；
3. 系统没有 Edge/Chrome 且 `allow_browser_download=true` 时，`_resolve_auto()` 会走 `_download_and_resolve()`；
4. Full 包表现为“Lite 包”，静默联网下载，正好违背 T05717 的核心目标。

另外，`launcher.py` 用 `_pw_dir.exists()` 决定环境变量：如果目录存在但为空（安全软件留下空壳），环境变量会指向 Program Files 下的只读目录，下载兜底会因无写权限失败，用户看到的却是“启动 Chromium 下载失败”，不是“安装包不完整”。

**触发场景：**

- Full 安装后 `playwright_browsers` 整个目录被删除；
- Full 安装后目录存在但为空，且系统无 Edge/Chrome；
- 旧 Full 升级/覆盖 Lite 后残留空目录。

**影响：**

T05717 的“Full 缺失内核不自动下载、明确报安装包不完整”在最常见的“整个目录消失”场景失效；用户可能被要求联网，或在 Program Files 下得到无权限错误。

**修复建议：**

不要把 Full 标记放在被校验的目录内部。建议在应用根目录写一个显式的 bundle manifest，由 Full/Lite 安装包分别携带：

```json
// release/xianyu-hunter/bundle-manifest.json
{
  "bundle_browser": true,
  "chromium_dir": "chromium-1255",
  "chromium_exe": "playwright_browsers/chromium-1255/chrome-win64/chrome.exe"
}
```

Lite 暂存目录写 `"bundle_browser": false`。运行时 `is_bundled_build()` 优先读根目录 manifest；没有 manifest 时再兼容旧包的 `chromium-*` 目录，并且必须用 `chromium_executable()` 确认完整，而不是只看目录名。

`launcher._setup_env()` 也要按 manifest 决定 `PLAYWRIGHT_BROWSERS_PATH`：Full（manifest=true）即使目录缺失也指向 app 目录，让运行时进入完整性错误；Lite 才指向用户可写目录。

最小改动版（不引入 manifest）：
1. Full 构建在 `release/xianyu-hunter/.xh-full-build` 再写一个根标记；
2. `is_bundled_build()` 先检查根标记；
3. Lite 暂存时删除该根标记；
4. `launcher` 检查根标记而不是仅 `_pw_dir.exists()`。

**测试补齐：**

- `playwright_browsers` 整个目录不存在，但根标记存在 → `is_bundled_build=True`，`resolve_kernel` 抛出完整性错误且不调用下载；
- 目录为空 → Full 报完整性错误，Lite 走用户目录下载；
- Lite 残留 `chromium-*/` 空目录 → `is_bundled_build=False`。

### H2. `-SkipBuild` 绕过 Full Chromium 完整性门禁，复跑结果不能作为门禁证据

**位置：** `scripts/build-publish.ps1:154-172`

```powershell
if ((-not $SkipBuild) -and ((Resolve-BundleBrowser) -eq "-BundleBrowser")) {
    ...
    if (-not ($markerOk -and $exeOk)) { ... exit 1 }
}
```

**问题：**

门禁被 `-not $SkipBuild` 包住，而 `-SkipBuild` 正是“发布已有产物”的正式路径。本次官方复跑 `scripts\一键发布.bat -SkipBuild` 退出码 0，但这一段根本没有执行；`publish-release.py` 只回查了资产 state/size，没有检查安装包里是否真的带 Chromium。

**触发场景：**

- 用旧版 build-exe 或手工替换 `release/xianyu-hunter` 后，直接 `-SkipBuild` 发布；
- Full 安装包内 Chromium 被替换成空壳，但发布目录仍有旧 marker；
- 构建阶段被绕过、只保留安装包。

**影响：**

可能把“无完整 Chromium 的 Full 包”发布出去，而发布日志仍显示成功。这是发布门禁失效，不是普通提示问题。

**修复建议：**

1. 把门禁与“是否重新构建”解耦：只要 `bundle_browser=true`，无论是否 `-SkipBuild`，都必须校验。
2. 更稳妥的做法是构建时生成 `build-manifest.json`，记录：
   - 安装包 SHA256；
   - `bundle_browser`；
   - Chromium 目录/可执行文件；
   - 构建时间、版本。
   发布前校验 manifest 与当前安装包哈希一致；`-SkipBuild` 也有据可查。
3. 如果 `-SkipBuild` 时 `release/xianyu-hunter` 已被清理，不能简单跳过；应直接失败，要求提供 manifest 或重新构建。

最小改动：

```powershell
$isBundle = (Resolve-BundleBrowser) -eq "-BundleBrowser"
if ($isBundle) {
    # 不再附加 (-not $SkipBuild)
    ...
}
```

### H3. 主资产按 LastWriteTime 选最新，未强制匹配当前版本，旧安装包可能被当成新包发布

**位置：** `scripts/build-publish.ps1:185-195、237-247`

```powershell
$matches = Get-ChildItem -Path $assetDir -File | Where-Object {
    ($n -like $glob) -and ($n -notmatch '(?i)-Lite\.exe$') ...
} | Sort-Object LastWriteTime -Descending
$asset = $matches[0].FullName
...
$ver = Get-AssetVersion $asset
```

**问题：**

主资产只按“最后写入时间最新”选，没有先用 `pyproject.toml` 的当前版本过滤。后果：

- `release` 目录同时有 `v0.4.20261126.1.exe` 和 `v0.4.20261126.2.exe` 时，只要旧文件被复制/恢复导致 mtime 更新，旧包会被选中；
- `-SkipBuild` 时又跳过了“必须早于流水线启动时间”的新鲜度检查（`237` 行），旧包可以畅通无阻；
- 符号链接资产的 `LastWriteTime` 可能是链接自身时间，不是目标文件时间，mtime 排序本身也不可靠；
- 最终 `$ver` 从选中的资产名推导，可能把旧版本发布到旧 tag，或者把旧包挂到新 tag 下。

**本次为什么没出事：** v2 的 mtime 恰好晚于 v1，是时间排序的偶然，不是逻辑保证。

**修复建议：**

先读当前版本，再精确取文件，不要先排序后猜版本：

```powershell
$expectedVer = Get-PyprojectVersion -root $RepoRoot
if (-not $expectedVer) { Write-Error "..."; exit 1 }

$expectedName = "XianyuHunter-Setup-v$expectedVer.exe"
$asset = Join-Path $assetDir $expectedName
if (-not (Test-Path -LiteralPath $asset)) {
    Write-Error "未找到当前版本安装包: $asset（release 中不得用旧版本代替）"
    exit 1
}
```

如果确实需要支持“最新产物但版本不同”，也必须先 `Get-AssetVersion` 并与 `$expectedVer` 比对，不一致直接失败。`-SkipBuild` 下这一步必须始终执行。

### H4. 发布不是原子的：Full 已公开后 Lite 失败会留下半成品 Release；替换上传先删旧资产

**位置：**

- `scripts/build-publish.ps1:282-304`：先发布 Full，再发布 Lite；
- `scripts/publish-release.py:381-405`：创建 Release 时按 `DRAFT` 直接决定是否公开；
- `scripts/publish-release.py:407-427`：同名资产先 `delete_asset`，再上传新文件；
- `scripts/publish-release.py:430-457`：上传失败重试 4 次，失败即退出。

**问题：**

`github_release.draft=false` 时，Full 的第一次 `publish-release.py` 调用就会创建“已公开”的 Release 并上传 Full。此时如果 Lite 上传遇到 TLS/网络错误：

1. Release 已经是 `draft=false`；
2. 用户能看到只有 Full 的正式 Release；
3. 脚本退出 1，但公开页面已经存在。

更严重的是替换同名资产：`delete_asset` 先删除线上旧资产，再上传新资产。如果上传重试全部失败，公开 Release 会失去该资产，而不是保留旧版本。

**触发场景：**

- GitHub TLS 抖动（本次首次 Python 发布就遇到 `SSL: UNEXPECTED_EOF_WHILE_READING`）；
- Lite 上传超时/断流；
- 同名资产体积变化，走替换上传。

**影响：**

发布结果可能是“公开但缺资产”“公开但只含 Full”，与“发布成功”日志不一致；用户下载到 404 或旧包。

**修复建议：**

改成三段式：

1. **创建草稿**（`draft=true`），不上传任何资产；
2. **上传并校验全部资产**（state、size、SHA256/digest）；
3. **最后 PATCH `draft=false`**，一次性公开。

`build-publish.ps1` 不应分别调用两次“创建并发布”；应让 `publish-release.py` 支持一次接收多个资产，或在 `build-publish` 中显式管理 draft id，最后统一 finalize。

替换已公开资产时，推荐：

- 先以临时名上传新资产（如 `...exe.new`）；
- 校验通过后删除旧资产；
- 通过 GitHub asset rename/PATCH 或重新上传为正式名完成切换；
- 失败时保留旧资产，不先删除。

本次的 `publish-curl.ps1` 已经采用了“draft → 上传两个 → PATCH 发布”的正确顺序，但其自身还有重入和校验问题（见 L1）；官方发布器应吸收这个顺序，而不是只把它当临时兜底。

### H5. Chromium 完整性只检查 `chrome.exe`，0 字节/缺 DLL 的内核也能通过构建与发布门禁

**位置：**

- `backend/xianyu_hunter/infra/browser_kernel.py:170-187`（`chromium_executable` 只 `is_file()`）
- `scripts/build-exe.ps1:503-521`（`Test-FullChromium` 只 `Test-Path`）
- `scripts/build-publish.ps1:159-166`（发布门禁同样只查 exe）

**问题：**

三处判据都只确认 `chrome.exe`（或 Linux 的 `chrome`）存在，不检查：

- 文件是否 0 字节/明显截断；
- `chrome.dll`、`resources.pak`、`icudtl.dat` 等关键依赖是否存在；
- Playwright 的 `INSTALLATION_COMPLETE` 标记；
- 可执行文件能否实际启动。

已复现：只创建一个 0 字节的 `chromium-1223/chrome-win64/chrome.exe`，`chromium_executable()` 仍返回该路径；构建脚本的 `Test-FullChromium` 和发布门禁也会通过。真机上启动时会报缺 DLL 或直接退出，但运行时不会给出“安装包不完整”的可诊断错误。

**触发场景：**

- 磁盘满导致复制只留下空文件；
- 杀软只隔离 `chrome.dll`，保留 `chrome.exe`；
- 缓存目录本身被截断；
- 手工把不完整目录放入 `playwright_browsers`。

**影响：**

Full 包标记为完整，实际无法离线登录；T05717 的诊断信息反而被绕过。

**修复建议：**

运行时至少验证关键文件：

```python
_REQUIRED_CHROMIUM_FILES = ("chrome.dll", "resources.pak", "icudtl.dat")

def chromium_executable(chromium_dir: Path) -> Path | None:
    for subdir, exe_name in _CHROMIUM_EXE_SUBDIRS:
        exe = chromium_dir / subdir / exe_name
        if exe.is_file() and exe.stat().st_size > 0:
            if all((exe.parent / n).is_file() for n in _REQUIRED_CHROMIUM_FILES):
                return exe
    ...
```

构建阶段再加一次真实启动校验：

```powershell
& $chromeExe --version *> $null
if ($LASTEXITCODE -ne 0) { throw "Chromium 无法启动: $chromeExe" }
```

`chrome.dll` 名称/资源文件随版本可能变化，建议以 Playwright 的 `INSTALLATION_COMPLETE` + 关键文件 + 启动 smoke 三重校验；至少不要只信一个 `chrome.exe`。

### H6. 发布“校验通过”只比较字节数，同体积不同内容会被当成同一资产

**位置：**

- `scripts/publish-release.py:215-240`（`verify_remote` 只比较 `size` 和 `state`）
- `scripts/publish-release.py:409-421`（同体积直接跳过上传）
- `scripts/build-publish.ps1:237`（本地只校验 mtime）

**问题：**

同一版本重新构建后，压缩后的安装包完全可能字节数相同但内容不同；当前逻辑会：

```python
if remote_size == size and existing_asset.get("state") == "uploaded":
    print("同名资产已存在且体积一致，无需重复上传")
    verify_remote(...)
    return
```

把“体积相同”当成“内容相同”，并输出“校验通过”。本次 Full/Lite 的实际 SHA256 与远端 `digest` 恰好一致，这是结果正确，不是校验逻辑正确。

**触发场景：**

- 重新构建同一版本，压缩结果大小碰巧相同；
- 上传被中间层替换/截断但字节数一致（概率低，但不能排除）；
- 远端旧资产与本地新资产同名同大小。

**影响：**

可能继续保留旧包却报告成功；发布门禁的“校验通过”不可审计。

**修复建议：**

GitHub Release asset API 已返回 `digest`（本次实测为 `sha256:<hex>`），直接使用：

```python
local_sha = hashlib.sha256(open(asset, "rb").read()).hexdigest()
remote_digest = (existing_asset.get("digest") or "").lower()
if remote_size == size and remote_digest == f"sha256:{local_sha}":
    # 真正的同内容，可跳过
else:
    # 体积相同但 digest 不同，必须替换；若远端无 digest，不要跳过
```

`verify_remote()` 也应优先校验 `digest`，`size` 只作为辅助条件。构建 manifest 中同时记录本地 SHA256，发布后回查远端 digest，才能形成完整证据链。

```python
ap.add_argument("--release-name", default=os.environ.get("GH_RELEASE_NAME"))
```

### M2. Lite 资产没有复用主资产的符号链接解析，PS 5.1 下会误报 0 字节/时间错误

**位置：**

- `scripts/build-publish.ps1:217-228`（只对主资产解析符号链接目标）
- `scripts/build-publish.ps1:295-300`（Lite 资产直接用 `Get-Item` 的 `Length`/`LastWriteTime`）

**问题：**

主资产已经处理了“磁盘紧张时 release 下的安装包是符号链接，Windows PowerShell 5.1 的 `FileInfo.Length` 返回 0”的情况，但 Lite 分支没有复用：

```powershell
$liteInfo = Get-Item -LiteralPath $liteAsset
if ($liteInfo.Length -le 0) { ... "Lite 安装包为 0 字节" }
```

如果 Lite 也是符号链接，会误报 0 字节；`LastWriteTime` 也可能取到链接自身时间，导致新鲜度判断错误。

**修复建议：**

抽一个 `Resolve-AssetCheckPath($info)` 函数，主资产和 Lite 都用；Lite 同时补 `min_size_mb` 下限（例如 20 MB），不要只判断 `>0`。

```powershell
function Get-AssetCheckInfo([System.IO.FileInfo]$info) {
    if ($info.LinkType -eq 'SymbolicLink' -and $info.Target) {
        $target = @($info.Target)[0]
        if (-not [System.IO.Path]::IsPathRooted($target)) {
            $target = Join-Path $info.DirectoryName $target
        }
        return Get-Item -LiteralPath $target
    }
    return $info
}
```

### M4. `GH_DRAFT=1` 时草稿 Release 无法回查，上传成功后 `verify_remote` 会失败

**位置：**

- `scripts/publish-release.py:182-186`（`get_existing_release_by_tag`）

**问题：**

GitHub 的 draft Release 尚未关联 tag，`/releases/tags/{tag}` 通常返回 404。当前脚本虽然支持 `GH_DRAFT=1`，但：

**修复建议：**

- `get_existing_release()` 先按 tag 查，404 时回退 `GET /repos/{repo}/releases` 列表，按 `tag_name` 匹配草稿；
- `verify_remote()` 接收 release id 或 release 对象，按 id 查询，不要按 tag；
- 把 `release_id` 写入 `.done.json` 或状态文件，重跑时优先复用。

### M5. `GH_DRAFT` / `GH_PRERELEASE` / `GH_DRY_RUN` 只设 true 不清 false，环境残留会覆盖配置

**位置：** `scripts/build-publish.ps1:278-280`

```powershell
if ($DryRun -or $rel.dry_run) { $env:GH_DRY_RUN = "1" }
if ($rel.draft) { $env:GH_DRAFT = "1" }
if ($rel.prerelease) { $env:GH_PRERELEASE = "1" }
```

**问题：**

脚本不会在配置为 false 时显式写入 `0` 或移除变量。`publish-release.py` 在导入时读取环境变量；如果当前 shell 或 `.env` 残留 `GH_DRAFT=1`，即使 `config.publish.json` 是 `draft=false`，也会按草稿发布；更严重的是复用已公开 Release 时 `update_release` 会 PATCH `draft=true`，把线上 Release 转为草稿。

`run-publish-v2.ps1` 只清了 `GH_DRY_RUN` 和 `CONFIG_PATH`，没有清 `GH_DRAFT`/`GH_PRERELEASE`。

**修复建议：**

```powershell
$env:GH_DRY_RUN   = if ($DryRun -or $rel.dry_run) { "1" } else { "0" }
$env:GH_DRAFT     = if ($rel.draft) { "1" } else { "0" }
$env:GH_PRERELEASE= if ($rel.prerelease) { "1" } else { "0" }
```

同样处理 `GH_REPO`，避免继承到别的仓库。

### M7. 发布门禁与构建脚本的内核判据不完全同口径

**位置：**

- `scripts/build-exe.ps1:512-518` 有“未知未来布局”的 glob 兜底；

## 4. 低优先级问题

### L1. `publish-curl.ps1` 是临时脚本，不应作为正式发布链

**位置：** `deliverables/t05717-build-2026-11-26/publish-curl.ps1`

两者 SHA256 相同。当前保留 ASCII 文件名是为了规避 PowerShell 5.1 读取 UTF-8 无 BOM 中文路径的问题，但双份文件以后修改容易只改一份。

`build-exe.ps1` 每次生成 `installer-lite.iss`，它不应作为源文件提交，也不应让 git 状态长期出现未跟踪文件。建议加入 `.gitignore`，并在构建文档中说明它由 `installer.iss` 派生。

### L5. 版本计数器丢失会让同日版本号倒退（附带发现）

**位置：** `scripts/update-build-version.ps1:46-62`

`.build-counter.json` 被 `.gitignore` 忽略。若在全新克隆/CI 上，当天已有 `0.4.20261126.2`，但计数器不存在，脚本会算出 `0.4.20261126.1`，版本号倒退，可能覆盖已有 Release。

建议：从当前 `pyproject.toml` 的版本提取同日 seq，取 `max(counter.seq, current_seq) + 1`；或者把计数器作为构建状态持久化到非代码目录。

### L6. 代码规范小问题

- `scripts/build-publish.ps1:185` 使用 `$matches` 作为自定义数组变量；`$Matches` 是 PowerShell 自动变量，容易被后续 `-match` 覆盖，建议改名 `$assetCandidates`。

1. **版本一致性通过：** `pyproject.toml` 与 `backend/xianyu_hunter/__init__.py` 均为 `0.4.20261126.2`，构建/安装包/Release tag 对齐。
